# 要件定義書 - DBMSコメント機能拡張とMarkdown出力カスタマイズ

## 1. 目的

tblsにおいて、コメント機能を持つDBMSから論理名とコメントを区切り文字で分離して管理し、Markdown出力で柔軟な表示カスタマイズを可能にする拡張機能を実装する。これにより、データベース設計書として論理名の表示、列順序の変更、列名の日本語化などを実現し、エンタープライズ環境での実用性を向上させる。

## 2. 機能要件

### 2.1 必須機能

#### 2.1.1 コメント解析・分離機能
- [ ] DBMSコメント内で設定可能な区切り文字による論理名とコメントの自動分離
- [ ] 論理名が取得できない場合の物理名へのフォールバック機能
- [ ] 区切り文字が存在しない場合の従来動作維持（後方互換性）
- [ ] 全DBMSオブジェクト（DATABASE、SCHEMA、TABLE、COLUMN、VIEW、INDEX、CONSTRAINT、FUNCTION等）への対応
- [ ] マルチバイト文字（日本語）を含む論理名の正確な処理

#### 2.1.2 Markdown出力カスタマイズ機能
- [ ] tbls.yml設定による列表示順序の任意変更
- [ ] 列名・項目名の多言語エイリアス表示（物理名→日本語名等）
- [ ] 論理名の表示/非表示切り替え
- [ ] オブジェクト種別別の個別設定（テーブル、カラム、ビュー等）
- [ ] 特定テーブル・オブジェクトへの個別カスタマイズ適用

#### 2.1.3 設定管理機能
- [ ] tbls.yml（.yaml）での統一的な設定管理
- [ ] 階層的設定（全体設定 > オブジェクト種別設定 > 個別設定）
- [ ] 設定値検証とエラーハンドリング
- [ ] デフォルト値による安全な動作保証
- [ ] 設定無効時の従来動作フォールバック

#### 2.1.4 対象オブジェクトの拡張
- [ ] **データベース**: 論理名・コメント分離、表示カスタマイズ
- [ ] **スキーマ**: 論理名・コメント分離、表示カスタマイズ
- [ ] **テーブル**: 論理名・コメント分離、列順序・エイリアス設定
- [ ] **カラム**: 論理名・コメント分離、列順序・エイリアス設定
- [ ] **ビュー**: 論理名・コメント分離、表示カスタマイズ
- [ ] **インデックス**: 論理名・コメント分離、表示カスタマイズ
- [ ] **制約**: 論理名・コメント分離、表示カスタマイズ
- [ ] **関数**: 論理名・コメント分離、表示カスタマイズ
- [ ] **その他DBMSオブジェクト**: トリガー、シーケンス等

## 3. 非機能要件


### 3.3 保守性

- 既存のtblsアーキテクチャとの整合性維持
- 可読性の高いコード実装（Go言語標準スタイル準拠）
- 包括的なテストケースによる品質保証
- 将来の機能拡張を考慮した設計

### 3.4 互換性

- **後方互換性**: 既存の.tbls.yml設定ファイルとの完全互換
- **対象DBMS**: サポートDBMS（PostgreSQL、MySQL、SQL Server、BigQuery）での動作保証
- **出力形式互換性**: 他の出力形式（JSON、YAML、PlantUML等）への影響なし

## 4. 制約事項

### 4.1 技術的制約

- **実装言語**: Go言語（既存コードベース）
- **対象出力**: Markdown形式のみ（他形式は対象外）
- **アーキテクチャ**: 既存のschema/、config/、output/パッケージ構造を維持
- **区切り文字**: 設定可能だが1文字または短い文字列に限定
- **依存関係**: 新たな外部ライブラリの追加は最小限に抑制

### 4.2 ビジネス制約

- **開発期間**: 段階的リリースによる機能提供
- **テスト環境**: 各種DBMSでの動作検証が必要
- **ドキュメント**: 設定例・マイグレーションガイドの整備

### 4.3 機能制約

- **DBMS制約**: コメント機能をサポートしないDBMSは対象外
- **文字制約**: DBMSごとのコメント長制限に準拠
- **設定制約**: 循環参照や矛盾設定の自動検出・回避

## 5. 成功基準

### 5.1 完了の定義

- [ ] **基本機能**: PostgreSQL、MySQL、SQL Serverでコメント区切り機能が正常動作
- [ ] **設定機能**: tbls.ymlでの区切り文字・列順序・エイリアス設定が正常動作
- [ ] **出力機能**: Markdown出力で論理名・カスタマイズされた列順序・エイリアスが正常表示
- [ ] **互換性**: 設定なし状態での従来通り動作の維持
- [ ] **品質**: 全既存テストのパス + 新機能テストの網羅的実装
- [ ] **性能**: 既存性能レベルの維持（ベンチマーク比較）

### 5.2 受け入れテスト

#### ユーザーシナリオ1: 基本的な論理名表示
1. データベースでカラムコメントを「論理名|説明」形式で設定
2. tbls.ymlで区切り文字を「|」に設定
3. tbls docコマンド実行
4. Markdownで論理名カラムが表示されることを確認

#### ユーザーシナリオ2: 日本語環境での使用
1. tbls.ymlで列名エイリアスを日本語に設定
2. tbls docコマンド実行
3. テーブル表で列名が日本語表示されることを確認

#### ユーザーシナリオ3: 大規模データベース
1. 1000テーブル以上のデータベースで実行
2. パフォーマンス劣化が5%以内であることを確認
3. メモリ使用量が適切な範囲内であることを確認

### 5.3 品質基準

- [ ] **静的解析**: golangci-lintでエラー・警告なし
- [ ] **テストカバレッジ**: 新規コードで90%以上、全体で既存レベル維持
- [ ] **実機テスト**: 主要3DBMS（PostgreSQL、MySQL、SQL Server）での動作確認
- [ ] **ドキュメント**: README更新、設定例整備、マイグレーションガイド作成

## 6. 想定されるリスク

### 6.1 技術的リスク

- **DBMS差異**: 各DBMSのコメント仕様差異による処理複雑化
  - **対策**: 早期のマルチDBMS検証、ドライバー別実装
- **パフォーマンス**: コメント解析による処理性能劣化
  - **対策**: ベンチマーク継続実施、最適化実装
- **文字化け**: マルチバイト文字処理での文字化け
  - **対策**: UTF-8での統一処理、文字エンコーディング検証

### 6.2 運用リスク

- **設定複雑化**: 多様な設定オプションによるユーザー混乱
  - **対策**: 段階的機能リリース、わかりやすいドキュメントの整備
- **移行コスト**: 既存ユーザーの設定移行負担
  - **対策**: 後方互換性確保、移行ガイド提供

### 6.3 保守リスク

- **コードベース拡大**: 機能追加によるコード複雑化
  - **対策**: モジュール設計、継続的リファクタリング
- **テストケース増大**: 組み合わせテストの複雑化
  - **対策**: 自動テスト強化、CI/CD改善
